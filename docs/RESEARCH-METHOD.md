# 研究纪律清单

这份清单里每一条都来自一次**具体的错**。写不出案例的规矩不收进来 —— 那种规矩没人会记住。

用它的方式：在写下一个结论之前，扫一遍这张表，问「我这条踩了哪一条」。

---

## 一、数字

### 1.1 每个数都要带分母

**案例**：我说「两个独立样本都过」，而那两个样本各是 1052 与 1032 只票。分母写出来之后，
第三个问题才浮现：它们**是不是真的独立** —— 而答案是不是（见 2.3）。

**反例**：「多数股票都涨」不算陈述，`454/1053` 才算。

### 1.2 每个数都要带基准

**案例**：我报过两个 `grid_classic` 的「0.1% 滑点」数：**−1.31%** 与 **+56.50%**。
前者基准是「相对买入持有该票」，后者是「相对沪深300」。差五十多个点，并排看会得出
「加了滑点它反而变好」这种荒唐结论。

**规则**：基准至少有两种，写清是哪种：
- 基准 A：相对**买入持有该票**（度量「有没有躲开下跌」，会奖励空仓）
- 基准 B：相对**沪深300**（度量「跑赢满仓指数」，仍混一份仓位管理的功劳）

同一个策略、同一样本、同一个滑点，A 与 B 的数**不可比**。

### 1.3 空着的格子是「没跑过」，不是「跑过没事」

**案例**：成本敏感性表里 `boll_revert` 那一格空了很久，读起来像「它没问题」。
实际是没跑。补跑之后它在基准 A 下**不过**（均值 −4.28）。

## 二、样本与时间

### 2.1 一个样本不能推整体

**案例（一天里三次）**：
- 上午：拿一个只差 0.01 的例子说「绝大多数是舍入」→ 中位数一算就穿
- 下午：拿一只票说 5 分钟策略「零成本就亏钱」→ 多验三只是**三负一正**
- 同一批：拿一只票的 5 分钟回测结果为 +218% → 那是复权 bug（见 3.2）

### 2.2 先标 n

**案例**：10:05 我发现「回撤越深越不过」这条线索在 4 个窗口上成立，**当场标上 n=4**；
10:10 加点到 8 个点，它倒了。
如果中间那次没标 n，它就会在验证之前被写进交接、当成一个「规律」。

**规则**：n ≤ 5 的「成立」只能叫**线索**，不能叫规律、机制、或结论。

### 2.3 概率性的东西，一次通过不算通过

**案例（同一天，同一个 bug 被推翻两次）**：
- 把 `max_tokens` 从 120 提到 800，**测了一次**，看到 `APPROVE` ⇒ 宣布修好
- 再测五次：`批准 / APPROVE / 批准 / 空 / 批准` ⇒ **推翻**（模型 4/5 答中文，而解析只认英文）
- 改提示词后测五次全过 ⇒ 又宣布修好
- 接上启动探针，**它当场报 CRITICAL** ⇒ **再推翻**（`reasoning_len=2907`，800 被推理全部吃光）
- 改成 4000、**连跑八次**全过。而八次的推理长度是 364 ~ 1749 —— 若还是 800，其中两次都会爆

**规则**：对**同一输入可能有不同输出**的东西（LLM、网络、并发、时间相关），
先问一句：

```
这个判据会以多大概率偶发通过？
```

- 若是「偶尔通过」⇒ 单次通过没有信息量，必须连跑
- 而「跑几次」不是拍脑袋：要看**观测到的波动范围**。
  上面那个例子里，看到 364 ~ 1749 就知道余量必须按最大值留，而不是按中位数。

**为什么它和 2.2（先标 n）不是一回事**：
2.2 说的是「样本少就别下结论」；这一条说的是「**对象本身是概率的，所以一次通过可能是运气**」。
前者是数量问题，后者是**性质问题** —— 而性质问题光加样本不能解决（我加了两次样本，
两次都被推翻，直到换了判据）。

### 2.4 「两个独立样本」可能是假的独立

**案例**：我一直说「两个独立样本都过」。而它们**都是在 2018–2026 全区间里抽的**，
共享同一段行情。按时间对切之后，前半不过（均值 −1.99）。
**「换一批票」与「换一段时间」是两件事。**

### 2.5 一个机制若真，就该能预言没见过的情况

**案例**：我说找到了「空仓的代价」这个机制，它的预言是「窗口涨得越多、空仓代价越大、超额越低」。
跑第二个策略去验：`corr(窗口大盘涨幅, 策略超额) = −0.1866`（n=6），方向对但太弱，
而且有一个明显反例（涨得第二少的窗口反而最差）。
⇒ 降级为「**讲得通的解释**」，不是「被验证过的机制」。

## 三、代码与数据

### 3.1 判据要覆盖「可能坏的东西」，不是我方便量的东西

**案例**：5 分钟数据抽查 30 只全过 —— 因为判据量的是**成交量求和**。
而真正坏的是**价格列**（全表 16.58% 为空）。判据正好绕开了那个真问题。

### 3.2 日频工具不能直接套到分钟频

**案例**：我把 11,640 个 5 分钟点直接喂给日频复权函数（它的输入契约是「一天一个点」），
它在每天内部反复应用同一个因子 ⇒ **复权比例从 1.02 涨到 36.82**，价格放大 36 倍
⇒ 算出的「0 滑点 +218%」是假的，修好之后是 **−29.72%**。

**规则**：有输入契约的工具，先问它的契约是什么，再问我的数据是不是那个形状。

### 3.3 路径与解释器别混

**案例（多次）**：
- 项目根本身在带日期的子目录里，我从 `dirname(dirname(__file__))/../兄弟仓` 找，
  少算一层 ⇒ 三个测试全报「数据不在手边」
- WSL 的 `python3` 没有 pymysql，用它跑读 DB 的汇总脚本 ⇒ `ModuleNotFoundError`
- **而我自己犯了这个错三次**：最后一次是刚写完这条规矩两分钟后，用 WSL python3 跑
  `check_acceptance_rules.py` ⇒ exit=1，而我**没看退出码就提交了**（又踩了 4.2）。
  ⇒ 说明这一条之所以难，是因为「用哪个 python」不是判据的一部分，而是一个习惯

**规则**：
- 兄弟仓从项目根**逐层往上找**，不写死绝对路径、也不靠层数猜
- **WSL python3** 做纯 json/统计；**Windows python** 读 DB 与 xtquant

### 3.4 工具要在它自己的仓里能跑

**案例**：我给旧仓的 `tools/rule_coverage_check.py` 加了一节「查数据字段填充率」，
里面写了 `import db`（并把它指向 `ROOT/data`）。跑起来报 `No module named 'db'`。

读了真实目录才知道：**`data/db.py` 在这个仓根目录下根本不存在**。
数据库访问是 `QuantCordis/data/db.py`（兄弟仓）—— 我这两天所有数据查询都在那个仓跑的。

⇒ 所以这是一个**跨仓依赖**，而我加它的时候**根本没想「这个工具在哪个仓」**。

**规则**：

```
① 加一个依赖前先问：它在这个仓里吗？还是兄弟仓的？
② 若是兄弟仓的 ⇒ 用「从项目根逐层往上找兄弟仓」的写法（不写死绝对路径、也不靠层数猜）
③ 而若那个兄弟仓不保证存在 ⇒ 要能优雅跳过（打印一行、返回成功），而不是崩
④ 而这类工具的「不可用」要写清楚：连不上就跳过，而不是假装量过了
```

**为什么它与 3.3（解释器别混）不同**：3.3 是「用了错的方式去跑它」，
这一条是「**我连它在哪都没想**」—— 是更前一步的疏忽。

**附**：这一条与 4.4 同源。「去代码或数据里找到它」的前提是**知道该去哪个仓找**。

### 3.5 装饰会让人搜不到自己写的话

**案例**：我给文档与代码注释加装饰性括号（在字与字之间插 `【` `】`、或在词后加 `**`），
目的是让人读起来有节奏。而后果是：

```
我写的是:   不【进【钩【子
我搜的是:   "不进钩子"
⇒ False
```

而同一天我用同样的方式搜过「第三种不可挂」（真实文本是 `第【三【种【不【可【挂`）⇒ **也 False**。

⇒ 于是出现了这个局面：**我读回了真实文件、确认注释确实在那里，而我的探针说它不在。**
两个信号矛盾，最后发现矛盾出在我自己的装饰上。

**而同一个形状还有另一面（同一天）**：**正则里的前缀也要从真实文本里拷**。

```
交接文件里那些小标题的真实形状是「> ### 2.1 …」（带引用符 `> `）
而我写正则时用了 `^### (2\.\d .+)$` —— 少了那个前缀
⇒ 它一条都匹配不到（打印出来是空的）

★ 而更要紧的是：**我在第 181 轮就已经知道这个文件里的标题带 `> `**
⇒ 所以这不是"不知道"，而是「**我知道真实文本长什么样，而我手里写的是另一个版本**」
   —— 与上面 ①②③ 是同一个形状。
```

**规则**：

```
① 要让人搜得到的话，就写成普通文本（不加装饰）
② 而「探针说不在」与「我读到它在」矛盾时，先怀疑探针的字符串是不是真实文本的子串
   （打印 repr 就看出来了）
③ 装饰是给眼睛的；而 grep 与脚本只认字节
④ **正则/锚点/搜索串：一律从真实文本里拷，不重打**（哪怕是刚刚看过的那一行）
   —— 因为"看过"不会变成"手里这份是对的"
```

**为什么它值得单列**：它不产生错误结论 —— 它产生的是**矛盾的信号**，
而矛盾的信号会让人怀疑自己刚读到的东西。这条比前几条更隐蔽。

### 3.6 日志是追加的 —— 所以「出现过」不是「现在这样」

**案例**：启动日志里 `[canary]` 有 3 行。而那个探针的约定是**通过打 1 行、警告打 3 行**
⇒ 所以我怀疑它正在报警。

而真相是：**那三行在文件的第 16–18 行（共 79 行）**，紧跟其后的是 `[live] 10:49:51 开始第 1 轮`
⇒ 它们属于 **10:49 那次启动** —— 而那时 `max_tokens` 还是 800（诊断里的 `usage=800` 就是证据）。
我在 **10:50** 才把它改成 4000 并重启过。

⇒ 所以现在跑的是新代码，那三行是**上一个版本留下的**。而我只数了「3 行」就下结论。

**规则**：

```
① 日志是追加的 ⇒ 同一个标签会同时出现「历史的」与「当前的」
② 所以看到一段输出时，先问：它属于哪一次启动 / 哪一轮？
③ 判别方法是**位置与上下文**，不是行数：
   往上看最近一条带时间戳的邻居，比只数行数可靠得多
④ 而如果那条输出自己带证据（这里是 usage=800），先读它 —— 它能直接定位版本
```

**为什么它值得单列**：它与前面几条不同 —— 前面几条是「判据量错了东西」，
这一条是**读到的信息本身是历史遗留**，而它看起来完全像当前状态。

### 3.7 先读真实那一行，再改

**案例（两次）**：
- 凭记忆猜锚点替换，锚点实际匹配 0 次 ⇒ 提交了一句假话（「筛选也把这个字段写进结果」）
- 猜 `run_backtest` 的签名是 `start=None, end=None`，真实是 `start, end`

**规则**：改之前 `grep` 出真实那一行。锚点不匹配时**拒绝写入**是正确行为 —— 那次是对的。

**而这条规则要比「读那一行」更严：锚点必须逐字节来自文件，不能凭记忆重写。**

**案例（同一天，第三次栽在锚点上）**：我要改交接文件的四处，锚点凭记忆写成：

```
> · `docs/RESEARCH-METHOD.md`（17 条，每条带案例）
```

而文件里真实的样子是（`repr` 打出来的）：

```
'> · docs/RESEARCH-METHOD.md（17 条，每条带案例）—— 做判断前扫一遍：'
```

⇒ 差别只是我**多加了两个反引号**。而它让锚点匹配 0 次 ⇒ 脚本 `exit` ⇒ **四处一处都没改**，
而我一直以为改完了 —— 直到读回来看见四项 `False`。

**做法**：
```
① 先把真实行用 repr 打出来（repr 会把不可见字符与标点如实呈现）
② 锚点直接从那份 repr 里拷，不重打
③ 而脚本里多处修改要**每处各自判断**，不要用「第一处失败就退出」——
   否则一处锚点错，后面几处静默不执行，而报告看起来像「改动了一部分」
```

### 3.8 小样本验证的是通路，不是数据形状

**案例**：5 分钟抓取第一版只挡了 `None`，没挡 `float('nan')` ⇒ 全量跑出
**97 成功 / 5088 失败**（`nan can not be used with MySQL`）。小样本上没暴露。

## 四、交付

### 4.1 文件会活着传播结论 —— 所以结论被推翻时要回去改

**案例（三次）**：
- 交接里写「5 分钟两个策略零成本就亏钱」→ 后来收回一半（三负一正）
- 交接里写「grid_classic 是唯一都过的」→ 时间对切推翻
- 交接里写「机制找到了」→ 预言失败，降级为「讲得通的解释」

**规则**：**进程会死，文件不会**。文件里的一句旧结论，会活到下一个会话里被当成新发现。
所以每推翻一次，就回去改一次，并把更正**放在最上面**，让「越上面越准」。

### 4.2 测一个守卫之前，先证明你的样本真的会让它失败

**案例（一天里两次，都是同一个形状）**：
- 想测「表格守卫会不会拦住坏提交」，我顺手 append 了一个「坏表格」⇒ 守卫报 ✓、提交还成功了。
  根因不是钩子：那个表格守卫**根本不认为它坏**。
- 想测「验收检查会不会拦住坏下单路径」，我往风控类加了一个 `_ALWAYS_APPROVE_FOR_TEST = True`
  ⇒ 守卫报 ✓、提交又成功了。根因同上：那个属性**不改变任何行为**。

**正确的一次**（同一天，第三次尝试）：换成我知道会失败的样本 —— **未闭合的代码围栏**
（Round 108 就是它让守卫红的）。先跑 `md_table_audit` 确认 `exit=1`，再测钩子 ⇒ 一次拦住。

**规则**：
```
① 先造样本
② 直接跑守卫，看退出码是不是非零        ← 这一步最容易跳过，而跳过就白测
③ 确认非零之后，再测钩子会不会用它拦住
```

**为什么难**：「编译通过」「能跑」和「它会红」是三件事。我第二次就是拿「编译通过」当成了「它会红」。

**而「判据通过」不等于「那件事成立」——它有三个具体的漏法**（同一天五次实例）：

```
(a) 样本不够坏
    · 「那个表格不算坏」          表格守卫不认它
    · 「加个属性不算坏」          那个属性不改变任何行为
    ⇒ 检测法：先证明你的样本真的会让它失败（就是这一条）

(b) 量错了对象
    · 「WARN 也算能解析」         量到了「降级路径」，而不是「模型会不会说话」
    · 「管道后面的退出码」        量到了 tail 的退出码，不是被测程序的
    ⇒ 检测法：问一句「它量的到底是哪个进程 / 哪条路径」

(a2) 「报得对」不等于「报得准」（判据分不清两个东西）
    · 钩子自检里两条检查**共用同一个正则**（`for t in md_table_audit privacy_scan`）
      ⇒ **删掉任意一个，两条都报缺** ⇒ 它会让人去找一个还在的东西
    · 而我第 171 轮"验证"过它：删掉**整个循环** ⇒ 报两条都缺 ⇒ 看起来是对的
      ⇒ **因为我的样本不够坏 —— 它区分不了两条**
    ⇒ 检测法：**样本要能区分**。要验 A 与 B 两条判据各自有效，
       就**分别只破坏 A 和只破坏 B**，看它是不是分别报对。
    ⇒ 实测（改后，三态）：
        只删 privacy_scan    ⇒ 缺 ['privacy_scan 每次跑']   ✓
        只删 md_table_audit  ⇒ 缺 ['md_table_audit 每次跑'] ✓
        复原                ⇒ 4/4 ✓

(b2) 样本被中间环节吃掉了
    · 我造了「未闭合的围栏」加在文件末尾 ⇒ 工具报 0 处 ✓ —— 而它**只查表格被打断**，不查这个
    · 我造了「打断表格的一行」加在真实文件末尾 ⇒ 又是 0 处 ✓
      —— 而直接调 audit() 证明：那一行的形状**确实会触发**（返回 1 处）
      ⇒ 它在真实文件里没触发，是因为**上下文**（那里可能在一个围栏里 / 或那个文件不在扫描清单里）
    ⇒ 检测法（最有效的一条）：**直接调那个函数，样本写进临时文件**
       —— 而不是「改真实文件、再跑整个工具」。后者有太多我不知道的中间环节。
    ⇒ 实测（五种样本，直接调 audit()）：
        打断行以 `|` 开头            ⇒ 0 处
        打断行不以 `|` 开头、以 `|` 结尾 ⇒ **1 处** ✓ ← 真正会触发的形状
        打断行两边都无 `|`            ⇒ 0 处
        干净表格                     ⇒ 0 处
        未闭合的围栏                  ⇒ 0 处

(c) 范围或口径太宽
    · 「数出 6 种」               那一段里有两组同样编号的列表，判据把两组混成一组
    ⇒ 检测法：把判据锚到它该量的那一段，而不是整个文件
```

⇒ **三者共同的形状**：判据报 ✓，而它量的不是那件事。
   而 (a) 已经被 4.2 条覆盖；这里补上 (b) 与 (c) —— 因为它们的检测法不同。

### 4.3 从没见它红过的守卫，不算守卫

**案例**：2026-10-16 给公开仓写隐私守卫（`tools/privacy_check.py`）并接进 pre-commit。
第一版有个缺陷：我写了「跳过这个判据文件自己」（因为它含通用模式字面量），而我的测试样本
**正好插在它身上** ⇒ 样本被吞掉、判据假通过。

于是那一版**被推上去了**，而它当时是一个**什么都不会报的守卫** —— 而钩子每次都会打印
`✓ privacy_check`。

**它比没有守卫更糟**：没有守卫时人还会自己看一眼；有了一个每次报 ✓ 的守卫，人就不看了。

**而能发现它唯一的原因是我测了它** —— 也就是 4.2 那条。这两条是一对：
- 4.2 说**怎么测**（先证明样本会让它失败）
- 4.3 说**为什么要测**（没红过的守卫给的是安全感，不是保护）

**自检问法**：这个守卫上一次红是什么时候？如果说不出，就当它不存在。

### 4.4 规则表与目标清单里的每一条，都要去代码或数据里找到它

**案例**：`docs/AI-TRADING-RULES.md` 的「§1 仓位与集中度（**硬上限**）」那张表有六条。
逐条去代码里找之后：

```
单票 20%        ✓ 有实现（实盘 84 次拒绝）
单日买入 10%    ✓ 有实现（实盘 4 次拒绝，理由带算术）
单一策略 30%    ✗ **代码里没有**
最低现金 5%     ✓ 有实现（真实的 if，只是还没触发过）
二级行业 ≤20%   ✓ 有实现
一级行业 ≤35%   ✓ 有实现
```

「单一策略 30%」**八种写法全空**：`0.3` / `strategy_cap` / `max_strategy` / `strat_mv` /
`_mv_by_strat` / 策略市值 / 同一策略 / `30%`。唯一命中的是一条无关的（波动率分档）。

⇒ 而它**不是「静默失效」，是从来没存在过**。写在「硬上限」表里、而代码里没有 —— 这比
「接上了但会跳过」更难发现，因为文档会让人以为它在那儿。

**规则两步走**：

```
① 换多种写法搜（因为不知道它叫什么）
② 做正向对照 —— 用同一个搜法搜几个你知道存在的写法，证明搜法有效
   （实测：0.05 ⇒ 2 处 · _cash_floor ⇒ 3 处 · sector_2 ⇒ 6 处 ⇒ 搜法有效）
```

只有②通过之后，「搜不到」才能翻译成「真的没有」。否则「搜不到」与「搜法坏了」分不清。

**而这是同一个失效家族的第四种形式**：

```
① 组件坏了，而日志说「风控在工作」               ← 事件 LLM 检查器
② 闸接上了，而数据缺失时静默跳过                 ← 行业闸的旧写法
③ 规则写在「硬上限」表里，而代码里根本没有它      ← 单一策略 30%
④ 改了规则，但没改状态                           ← .gitignore 与锚点替换
```

**④ 的两个实例（同一天）**：

```
· 把三个运行产物加进 .gitignore ⇒ 只对其中的两个做了 `git rm --cached`
  ⇒ 「看起来生效」（git status 里不显示了），而那个文件还在库里
  ⇒ 直到它下次被改动，git 才提示。

· 用锚点替换改文件 ⇒ 锚点没匹配、什么都没改
  ⇒ 「看起来生效」（我接着跑的测试报了 ✓，而它测的是旧文件）
  ⇒ 直到我读回真实文件才发现。

⇒ 共同点：**举动只做了一半，而「看起来生效」了** —— 两个假象。
  而 ④ 的检测法就是 4.5 条：**读回真实状态**，而不是看某个间接信号。
  附：`.gitignore` 只对**未跟踪**的文件生效；对**已经在库里**的必须显式 `git rm --cached`。
```

**而它该配的自检**：把规则表逐条映射到「代码里的哪一行」，做成一个清单。
映射不出来的那一条，就是要问用户「是实现它，还是改文档」的那一条。

**而这条规则要再扩一步：不只「代码」，还包括「数据字段」。**

**案例（同一天发现的）**：目标方向 (2) 写的是「补 amount 字段 · 复权口径统一 ·
需要时补港股通数据」。而我这两天验过复权口径（A 类缺口 3019 ⇒ 0）、验过 5 分钟
（6014 万行、价格空行 0）、验过指数（4 个）—— **而「amount 字段」我从来没量过。**

量出来（分母写清楚）：

| 表 | 总行数 | NULL | =0 | >0 |
|---|---|---|---|---|
| `quantcordis_bar_none`（日K） | 16,247,753 | 0 | 467,876（2.88%） | 15,779,877（97.12%） |
| `quantcordis_bar_5m`（5 分钟） | 60,143,001 | 0 | 113,200（0.19%） | 60,029,801（99.81%） |

⇒ 两张表都填上了。而它一直是「已经做了」的样子，两天没被量过。

**所以「找到它」有三层**：

```
① 代码里有它（规则映射到代码行）      ← 原来的 4.4
② 数据里有它（字段真的被填充）        ← 本次扩的
③ 而两者都要**量**，不是"看一眼觉得在"
```

### 4.5 一个仓里的覆盖漏洞，另一个仓里大概率也有

**案例一（覆盖范围）**：

```
另一个仓里：md_table_audit 只扫根目录 ⇒ docs/ 下 13 个文档从没被扫过
⇒ 把 docs/ 加进扫描 ⇒ 立刻 5 处（3 真 2 误）
⇒ 而按这条规则去查公开仓 ⇒ 它根本没有这类检查，而 docs/ 下有 24 个文档（更大）
```

**案例二（同一个坑的另一个方向）**：

```
第 3.4 条：工具【依赖】兄弟仓（import db 失败）
⇒ 同一天又出现：文档【提到】兄弟仓（引用检查报"文件不存在"）
⇒ 而第三次出现时，让检查自己说出修法：「若是兄弟仓的文件，把它加进白名单」
```

**规则**：

```
① 修完一个覆盖漏洞，去问：另一个仓里有没有同一个洞？
② 而"另一个仓"不一定是同类的两个仓 —— 同一个坑可能以另一个方向再现
   （依赖 / 引用 / 路径 / 命名）
③ 而它的价值是：把"修一个实例"变成"修一类"
```

**为什么值得单列**：它省钱。查另一个仓的成本是几分钟，而漏掉它的代价是——
那个仓的 24 个文档继续没人看，而它正是别人会克隆的那一个。

### 4.6 改文件与测它，不在同一次调用里

**案例（同一天，同一个坑埋了两次）**：

- 想给 pre-commit 加一条检查，用「找到某行注释、替换成新块」的写法，脚本报了 `x 锚点 0`
  ⇒ 而我在**同一次调用里接着跑测试** ⇒ 测试跑的是**改之前**的钩子、报了 ✓
  ⇒ 我以为改成功了，提交了，而提交信息说的是「挂进 pre-commit」。
- 读回真实文件才看到：**钩子只有 38 行、里面根本没有那条检查**。
- 而更早一次也一样（提交信息说「第三个守卫接入钩子」，而加完之后文件里含该标记的行 = 0）。
  当时「验证」看到的 `✓ md_table_audit` / `✓ privacy_scan` **都是真的** ——
  因为那是改之前的钩子本来就有的输出。

**形状**：

```
改的动作失败了 → 同一次调用里测它 → 测到的是改之前的东西 → 报 ✓ → 写了假信息
```

**而两次失败都只打印了一行 `x 锚点 0`** —— 一个没有被检查的返回值，被后面那句「验证通过」淹没了。

**规则**：

```
① 改完之后，下一次调用只做一件事：读回来确认（行数、关键词、结构）
② 行为测试再下一次调用
③ 而且要检查改的动作自己的返回值 —— 它失败时说的话，就是它唯一的信号
```

**附：同一个错在命令层面也犯过两次**

```
我写 `bash tools/hooks/pre-commit 2>&1 | tail -6 | sed ...; echo exit=$?`
⇒ 读到的 $? 是 **tail** 的，不是钩子的 ⇒ 明明拦住了提交，却报了 exit=0。

修法：要测退出码就别接管道，重定向到文件再读：
    bash tools/hooks/pre-commit > /tmp/out.txt 2>&1; rc=$?
```

**附：为什么「锚点替换」特别容易出这个错**
它失败时**什么都不改**，所以文件看起来完全正常（就是旧的）。而「整份重写」失败时会留下
一个明显坏的中间状态。⇒ **复杂改动宁可整份重写**，改完也一样要读回来。

### 4.7 能变成检查的规矩，就不要只留在纸上

**案例（就在写这份清单的同一天）**：

```
· 隐私守卫拦了我 4 次 —— 而"公开仓库不许出现只对本机成立的东西"这条规矩，
  是我自己当天上午写进交接文件的。
· 而反过来：钩子报出 3 处真实的文档缺陷（围栏没关闭、正文被吃进代码块）——
  那些我从来不知道它们存在。

⇒ 所以当天真正管用的是机制，不是规矩。
```

**规则**：

```
每写下一條规矩，就问一句：它能不能变成一个检查？
  · 能 ⇒ 去做那个检查。因为规矩会腐烂，而检查不会。
  · 不能 ⇒ 那就在规矩里写清楚「怎么判断自己违反了它」——
           例如 2.3 条给了"先问这个判据靠运气通过的概率有多大"这个动作。
```

**而它管着前面所有条** —— 因为每一条都可以问这个问题：

```
1.1 带分母            ⇒ 能（检查每个数字后面有没有分母）
2.3 一次通过不算通过   ⇒ 难以机械化，但给了「先估运气概率」这个动作
3.4 工具要在自己仓里跑 ⇒ 能（导入时检查路径来源）
3.7 先读真实那一行     ⇒ 能（改之前先 grep 出真实行再比对）—— 而今天已经有三次教训
4.4 去代码或数据里找到它 ⇒ 能（rule_coverage_check.py 就是它）
```

**而它当天就抓到了我一次（最好的证据）**：

```
我把 `rule_coverage_check.py --only-doc` 改名成 `--fast`（因为那个名字在说谎 ——
它其实还查钩子自检，不只查文档）。
⇒ 而钩子自检里那个模式串还写着旧的 `--only-doc` ⇒ **它立刻报「缺：文档漂移检查每次跑」**
⇒ 而那正是我漏改的地方 —— 靠"记得去改所有地方"我一定会漏掉它。
```

**而它当天第二次抓到我：改名只改了一半**

```
我把 `--only-doc` 改成 `--fast`，机制抓到我漏改钩子自检里的模式串（见上）。
⇒ 但"抓到我"不等于"改完了" ⇒ 于是我**把旧名字全仓搜了一遍**：
     RESEARCH-METHOD.md（2 处）  ⇒ 那是本条规则的案例，引用旧名字是必要的 ✓
     rule_coverage_check.py（5 处）⇒ 那是别名定义与它的注释 ✓
     tools/hooks/pre-commit:21     ⇒ **钩子的说明注释还写着旧名字** ✗ ⇒ 改
⇒ 而那一行改的时候才发现：**它的说明也和名字一起说错了** ——
   它写「文档引用的代码行是否真的存在」，而那个模式跑两件事。
```

**所以第 4.7 条的操作版是**：

```
① 能机械化 ⇒ 去做那个检查（本条）
② 不能机械化 ⇒ 在规矩里写清「怎么判断自己违反了它」
③ 而"改名 / 换路径 / 换接口"这类 ⇒ **先把旧名字全仓搜一遍，再一个一个判断** ——
   因为机制只能抓它被写去抓的那几处
```

**为什么它值得排在最后却最重要**：前面每一条都是「我该怎么做」，
而这一条是**「我该把哪一条变成我做不到违反的东西」**。

### 4.8 让被测的东西自己说出它是什么

**案例一（同一天，一个假守卫）**：我给验收检查加了一条：造「200 条拒绝 + 1 条真买单」的状态，
调 `run()`，看闸②拒得对不对。它通过了 —— 而**它测不到那件事**，因为
`run()` 调的是 `_handle_signal`，而**截断发生在它的调用者 `run_once` 里**。

```
检测法（很简单）：看它测完之后、**被测的对象有没有被改变**
⇒ 而这里窗口从 200 变成 **201** ⇒ 说明它没截断、也就没测到要测的东西。
```

**案例二（同一轮，改一个函数却改到了文档）**：我想把 `_trim_orders` 临时改回一刀切，
用 `s.index('    keep_today = [o for o in orders')` 定位 ——
而**那个字符串首先出现在我自己写的 docstring 里** ⇒ 我改的是文档。

```
检测法：`inspect.getsource(f)` 打出它真正执行的源码
⇒ 两次输出一模一样 ⇒ 说明第二次改动没生效。
```

**规则**：

```
① 改一个函数之后，用 `inspect.getsource(f)` 看它**真正**是什么 —— 而不是你以为是什么
② 测一个东西之前，先看**它测完之后被测对象有没有被改变**
   （没变 ⇒ 它可能根本没走到那一步）
③ 而「我以为它调的是 A」与「它调的是 A 的前一步」是两种不同的错 ——
   后者更隐蔽，因为两边的名字都对
```

**为什么它值得单列**：今天这一类（「我以为它测的是 A，而它测的是 A 的前一步」）
是最隐蔽的一种 —— 而它有一个**一眼可见的检测法**。

### 4.9 守卫要绿着提交

**案例**：多次先提交、再看守卫退出码，然后回头补一次提交。
正确顺序是：跑守卫 → 看退出码 → 绿了再提交。
